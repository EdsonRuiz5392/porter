# TC-012 — Fragmentación y mensajes inválidos

**Requisitos cubiertos:** RF-21, RF-22, RNF-14, RNF-24.
**Nivel:** integración. **Hito:** H2 (local) · H3 (remoto).

## Objetivo
Comprobar que el protocolo tolera mensajes fragmentados y pegados, y que responde con un error a los inválidos sin caerse.

## Precondiciones
Servicio reiniciado con la configuración de abajo y `/tmp/porter-tc` limpio, según la [preparación común](README.md).

## Entorno y configuración
Preparación común, con Valores por defecto.

## Datos de entrada
Un mensaje enviado byte a byte, dos mensajes pegados, una longitud de 2 GB, JSON inválido y JSON que no es objeto.

## Pasos reproducibles
**Automatizado:**

```bash
python3 verif/scripts/run_verificacion.py --filtro tc012
```

**A mano:**

1. Con un cliente de prueba, enviar `health` byte a byte.
2. Enviar `list` y luego `health` y `list` pegados en una misma escritura.
3. En conexiones nuevas, enviar cada mensaje inválido.
4. Revisar `PROTOCOL_ERROR` en la bitácora y `porter health`.

## Resultado esperado
- Se reciben las cuatro respuestas válidas, en orden.
- Cada mensaje inválido recibe `error` con `INVALID_REQUEST`.
- Hay 3 eventos `PROTOCOL_ERROR`.
- El servicio sigue vivo.
